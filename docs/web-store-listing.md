# stitaP Capture — Chrome Web Store listing & signed updates (Phase E)

Everything needed to take `extension/` from "load unpacked" to a published,
auto-updating store item. What is done in this repo, what needs a human:

| Artifact | Status |
|---|---|
| `scripts/package-extension.ts` — validates the manifest + zips `extension/` | ✅ in repo |
| `extension/releases/stitap-capture-v0.4.0.zip` | ✅ generated by the script |
| Store icons (`extension/store/icon-440.png`, `marquee-1280x800.png`) | ✅ generated |
| Listing copy, permissions, privacy text (this doc) | ✅ in repo |
| Real screenshots (1280×800 UI captures) | ⚠️ human — no Chrome in dev env |
| Uploading to the dev console, publishing, store review | ⚠️ human — needs a Google account |

## 0. Quick start

```bash
bun run gen:extension-icons   # icons + store assets (run once / after logo changes)
bun run package:extension     # extension/releases/stitap-capture-v<version>.zip
```

Upload the zip at <https://chrome.google.com/webstore/devconsole>, fill the
listing below, and publish.

## 1. Listing copy

### Title (≤ 30 chars)

```
stitaP Capture
```

### Short description (≤ 132 chars)

```
Capture the page you're viewing — viewport or full page, as a PNG. Pixels only: no credentials, cookies, or form data leave your browser.
```

(119 chars.)

### Category

`Productivity` (Developer Tools is also defensible; Productivity matches the
editor-first audience.)

### Detailed description

> **Capture any page — even ones a URL service can't reach.**
>
> stitaP Capture grabs the tab you're already viewing: authenticated apps,
> VPN-gated intranets, and local dev servers that a headless capture service
> can never log into. It works because *you* are already signed in — and only
> rendered pixels ever leave the browser.
>
> **What you get**
>
> - **Viewport capture** — one click, a PNG of exactly what's on screen.
> - **Full-page capture** — scrolls the whole page (lazy content loads first,
>   capped at 100,000 px), pauses animations and videos, and stitches the
>   tiles into one image in an offscreen document.
> - **Clean headers** — fixed/sticky elements are captured once at the top and
>   once at the bottom instead of repeating in every slice.
> - **Save to your stitaP library** — the capture flows into the open stitaP
>   workspace where it can be annotated, redacted, and exported as SVG.
> - **Restore, always** — scroll position, animations, and videos are put back
>   exactly as you left them, even if a capture fails.
>
> **Privacy by design**
>
> Only page pixels, the page URL, the tab title, and viewport dimensions ever
> leave your browser — transmitted to your own stitaP workspace account so you
> can edit and export the capture. No credentials, cookies, form values, DOM
> text, or request headers. The extension reads no other sites: clicking the
> icon grants access to the active tab only (`activeTab`), and the only site
> it can message is the stitaP app itself.

### Permissions shown at install

The store will display:

- **Read and change your data on freebuff.app / vly.sh** — scoped to the stitaP
  workspace origins only. This is the upload channel: the popup relays the
  stitched PNG to the signed-in workspace tab, which performs the upload. No
  broad site access is declared, so there is no "reads all sites" warning.
- **activeTab**, **scripting**, **storage**, **offscreen** — see §2 for the
  justification text to paste into the "Permission justification" field.

### Support / website

Point these at the stitaP product's support page and repository (set to the
live URLs at submission time). A support email is required if you host one.

## 2. Permission justifications (paste into the console)

| Permission | Why it's needed |
|---|---|
| `activeTab` | Only grants access when the user clicks the toolbar icon — the capture trigger. Keeps the "reads all sites" warning off the install dialog. |
| `scripting` | Injects the content script (freeze / scroll / restore) into the active tab when the user starts a capture. |
| `storage` | Remembers the last-seen stitaP workspace origin so the popup can offer "Open stitaP to sign in". |
| `offscreen` | Runs the tile-stitching worker off the popup thread (MV3 has no background page for DOM/canvas work). |
| `host_permissions` (stitaP origins only) | Lets the popup find and message the user's signed-in stitaP workspace tab, which is the uploader — the extension itself never holds a session or credentials. |
| `tabs` (none) | Not requested. `captureVisibleTab` works through `activeTab`. |

## 3. Privacy — required disclosure + ready-to-paste policy

Chrome Web Store requires **both** a privacy section in the listing and a
hosted privacy policy URL (any public URL — a GitHub Pages page or a `#privacy`
anchor on the stitaP site works). The listing privacy section:

> **Data used & transmitted:** when you capture a page, the extension sends
> the rendered image, the page URL, the tab title, viewport dimensions, and a
> timestamp to your own stitaP workspace account (the app you're already
> signed into) so the capture can be saved, annotated, and exported. This is
> user-directed data flow: nothing is sent unless you click Capture.
>
> **Data collected by the extension itself:** none. No analytics, no
> telemetry, no account, no remote code.
>
> **Third parties:** none. The extension communicates only with the stitaP
> workspace origins listed in the permission notice.
>
> **Retention:** captures live in your stitaP library under your account and
> can be deleted there at any time.

Host this text at a public URL and paste the link into the **Privacy policy**
field. Suggested host: a `PRIVACY.md` rendered via GitHub Pages, or a
`/privacy` page on the stitaP site.

## 5. Publish checklist (dev console)

1. **Create the item** — dev console → *New item* → upload
   `extension/releases/stitap-capture-v0.4.0.zip`.
   - If the manifest fails validation, the console names the field; fix and
     re-run `bun run package:extension`.
2. **Store listing tab** — paste §1 copy, §2 justifications, privacy policy
   URL, icon, screenshots.
3. **Visibility** — start as **Private** (only people added in the tester
   group can install) → install from the dev console, sanity-check the
   capture flow against a live stitaP deployment → move to **Public**.
   - Testers: create a Google Group and add its address in *Publish to testers*.
4. **Submit for review** — the first review can take up to a few days; later
   updates are usually faster. You can keep shipping code while it's in review.
5. **After approval** — the item goes live; users install from the store.

## 6. Signed updates (how users get new versions)

- **Chrome Web Store = the signed update channel.** When you publish a new
  version, the store signs it with the item's key and pushes it to every
  installed client automatically — there is no separate signing step.
- **Version bumps:** edit `extension/manifest.json` → `version` (must be
  `N.N.N` and higher than the previous one; `version_name` can carry
  pre-release labels like `0.5.0-beta`) → re-run
  `bun run package:extension` → upload the new zip → **Submit for review**.
  The zip filename follows the version, so old packages are never overwritten
  accidentally.
- **`update_url` / self-hosting:** do **not** add `update_url` to the
  manifest. Hosted CRX updates (self-signed `update_url` manifests) are a
  deprecated, enterprise-only path — Google removed support for installing
  them for the general public. Store-hosted updates cover the normal case.
- **Key warning:** once an item is on the store, its upload key is fixed. You
  cannot move the item to a self-hosted distribution later, and losing the
  store account means losing the item — keep the developer account tied to a
  durable Google account with recovery options.
- **Testing updates:** publish pre-release builds to the *testers* group
  first; testers get the update through the same store channel, then you
  promote to public after a clean pass.

## 7. What's deliberately out of scope

- **Auto-update verification in CI** — the store does the signing; there is
  nothing to verify locally beyond the zip round-trip (`unzip -l`).
- **Real screenshots / browser E2E** — require Chrome; the environment that
  builds this repo has none. See `docs/roadmap.md` → *Testing/QA*.
